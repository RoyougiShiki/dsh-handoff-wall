# v0.5 关联主轴视图：静态数据派生，与 talkmap 弃用不冲突

用户反馈（上一条对话的 T16）指出：时间线视图的重点应是 Talk-map 式的「关联」——某个对话确定摘要后、后来被哪个对话节点接续/引用做了交接——而不是字面时间先后。但既有文档里 spec §5.5 把时间线墙定义为「按 createdAt 定位的纯 CSS 泳道」，ADR-0001 又记录 talkmap 因给活跃会话滚动烧 LLM 摘要而被弃用。两条记录合在一起，容易让人误以为「关联视图 = talkmap = 弃用」。

本 ADR 澄清二者关系，并定调 v0.5 的视图方向。

## 决策

- **视图主轴改为「交接关联」**：以 `notes.parentSessionId`（`''`=首条）为血缘键建树，按「交接族」分组；🤖 子代理与正式条按血缘缩进挂父卡下；跨工作区父会话补成虚线「外部原对话」节点；家族按子树最新活动倒序。
- **每张卡显式标注反向关联**：「↳ 被 N 接续」「源: 前 8 位父 id」；进行中/🤖子代理/↪外部 徽章；时间退为卡片内次级标签。
- **talkmap 弃用仅指「LLM 滚动摘要」这一类采集器**：v0.5 关联视图由静态账本字段（`parentSessionId`、`kind`、sessionQuery 的 live/persisted 状态）直接派生，无任何 LLM 调用、无后台写入，与 ADR-0001「零后台进程」原则完全一致，不构成复活 talkmap。
- **数据层早已具备关联基础**：`parentSessionId` 即「父对话→交接条→子对话」的接续链；`who_else` 是现在时（活会话）的关联查询。缺的只是 UI 重心与文档定义，不是数据——本次补齐。

## Considered Options

- 保留「按 createdAt 的泳道」、把关联仅作缩进装饰：被否——用户明确要「关联式呈现」为一等公民，纯时间排序被反馈为「只是按时间排序的列表」。
- 复活 talkmap 画布（React Flow / LLM 摘要）：被否——talkmap 弃用根因（活跃会话滚动烧 LLM）未变；关联关系用静态数据即可表达，无需自由画布与 LLM。

## Consequences

- 时间退为次级标签，家族按「子树最新活动」倒序而非全局 createdAt。
- 外部原对话以虚线节点呈现，不要求父条同库存活。
- 自由画布 / 拖拽布局 / 缩放仍属雾区（不引入 React Flow），不因此重启 talkmap。
- 文档责任：spec §5.5 相应改为关联主轴描述；本 ADR 作为方向调整的决策依据。
